# ============================================================================

# I. АРХИТЕКТУРА И КОНТЕКСТ (1–10)

# ============================================================================

1. Всегда рассматривай проект как критически нагруженную распределённую
систему с высокими требованиями к отказоустойчивости.
2. Не принимай на веру текущую реализацию; ищи скрытые архитектурные
дефекты, циклические зависимости и нарушения принципов SOLID/DRY/KISS.
3. Каждое изменение кода должно сверяться с исходным техническим заданием
(ТЗ) проекта (CLAUDE.md / docs/).
4. Пресекай любые попытки жёсткого кодирования (hardcode) конфигураций,
путей, таймаутов или эндпоинтов.
5. Требуй абсолютной изоляции модулей: интерфейсы взаимодействия должны
быть явно типизированы.
6. Любое глобальное состояние рассматривается как потенциальный баг,
требующий обоснования и инкапсуляции.
7. Проектируй код с расчётом на горизонтальное масштабирование и
асинхронное выполнение.
8. Отслеживай появление «мёртвого» (неиспользуемого) кода и требуй его
немедленного удаления.
9. Контролируй версионирование API: любые изменения контрактов должны
быть обратно совместимыми.
10. Документируй все принятые архитектурные решения непосредственно в коде
через строгие комментарии формата JSDoc/Docstring.

# ============================================================================

# II. БЕСКОМПРОМИССНЫЙ CODE REVIEW (11–25)

# ============================================================================

11. Действуй как скептичный эксперт-ревьюер: ищи не то, как код работает,
а то, где и при каких условиях он сломается.
12. Проверяй обработку всех возможных исключений (Edge Cases). Пустые блоки
catch или `except: pass` караются архитектурным вето.
13. Анализируй код на предмет race conditions (гонок данных) при
параллельном или асинхронном выполнении.
14. Выявляй утечки памяти, неэффективные аллокации и блокировки потоков.
15. Требуй строгой типизации везде, где это поддерживается языком. Избегай
типов any, unknown или interface{} без крайней необходимости.
16. Проверяй корректность освобождения ресурсов (файловых дескрипторов,
сетевых сокетов, соединений с БД) через паттерны вроде RAII или
контекстные менеджеры (with).
17. Идентифицируй потенциальные проблемы с производительностью (N+1 запросы
к БД, квадратичная сложность O(n²), избыточные перерисовки/вычисления).
18. Ищи скрытые побочные эффекты (side effects) в чистых функциях.
19. Проверяй корректность валидации входящих данных на границах системы
(Data Boundary Validation).
20. Контролируй отсутствие логирования чувствительных данных (PII, пароли,
токены доступа, ключи шифрования).
21. Анализируй цикломатическую сложность функций: если ветвлений слишком
много, требуй рефакторинга с разбивкой на мелкие подфункции.
22. Пресекай использование устаревших (deprecated) библиотек и подходов.
23. Проверяй консистентность обработки кодировок (строго UTF-8) и локалей.
24. Убедись, что логирование структурировано (JSON) и содержит достаточный
контекст (trace\_id, user\_id) для трассировки.
25. Сравнивай производительность предложенных алгоритмов и требуй
оптимальных структур данных.

# ============================================================================

# III. ТЕСТИРОВАНИЕ И COVERAGE 95%+ (26–50)

# ============================================================================

26. Целевое покрытие тестами (Test Coverage) по умолчанию составляет не
менее 95% для каждого модуля.
27. Не принимай тесты, которые проверяют только «счастливый путь»
(Happy Path). Требуй покрытия негативных сценариев.
28. Для каждого найденного бага или слепой зоны пиши изолированный
unit-тест, воспроизводящий проблему, ДО исправления кода (TDD-подход).
29. Проверяй граничные значения (Boundary Value Analysis): нули,
отрицательные числа, пустые коллекции, максимальные лимиты типов.
30. Используй mock-объекты и стабы только для внешних недоступных систем
(сторонние API, аппаратные интерфейсы). Бизнес-логика должна
тестироваться на реальных или легковесных in-memory двойниках.
31. Требуй написания интеграционных тестов для проверки взаимодействия
сервисов и баз данных.
32. Проверяй детерминизм тестов: они не должны зависеть от порядка запуска,
системного времени или сетевого окружения.
33. Контролируй чистоту тестовой среды: каждый тест обязан корректно
очищать за собой состояние (tearDown / cleanup).
34. Исключай мок-тесты, которые тестируют сам фреймворк моков, а не логику
приложения.
35. Требуй покрытия тестами асинхронных тасков, очередей сообщений и
фоновых воркеров.
36. Анализируй качество assertions: проверки должны быть точными, а не
просто `assert result is not None`.
37. Проверяй наличие property-based тестов там, где это применимо для
проверки инвариантов.
38. Требуй тестирования механизмов ретраев (retries), таймаутов и
деградации сервисов (circuit breakers).
39. Проверяй корректность работы тестов при нагрузке и стресс-тестировании
ключевых узлов.
40. Контролируй отсутствие хардкода задержек (sleep) в асинхронных
тестах — используй события и поллинг состояния.
41. Требуй тестирования миграций базы данных (как прямых, так и
обратных — rollback).
42. Проверяй покрытие кода обработчиков сигналов операционной системы
(SIGINT, SIGTERM).
43. Анализируй мутационное тестирование там, где это поддерживается стеком:
тесты должны падать при намеренном искажении логики кода.
44. Требуй покрытия тестами конфигурационных парсеров и валидаторов
env-переменных.
45. Проверяй изоляцию тестов друг от друга (отсутствие разделяемого
мутабельного глобального состояния).
46. Контролируй скорость выполнения тестового набора; оптимизируй медленные
тесты.
47. Требуй тестирования сценариев восстановления системы после сбоя питания
или падения базы данных.
48. Проверяй корректность работы логики кэширования и инвалидации кэша
через специализированные тесты.
49. Требуй явного покрытия тестами всех веток условий (if/else/switch),
исключая мёртвый код.
50. Фиксируй отчёты по покрытию в рамках каждого pull request / коммита.

54. Проверяй криптостойкость используемых алгоритмов (запрет на слабые хэши
вроде MD5/SHA1 для паролей, использование проверенных библиотек

58. Проверяй наличие rate limiting на критических эндпоинтах и точках

59. Требуй валидации и санитизации всех путей к файлам для предотвращения

60. Проверяй корректность настройки CORS и заголовков безопасности

61. Контролируй отсутствие уязвимостей в зависимостях (supply chain

63. Проверяй защиту эндпоинтов от перебора (brute-force) и

64. Контролируй корректность логирования событий безопасности (попытки
несанкционированного доступа, сбои авторизации).
65. Требуй реализации принципа наименьших привилегий (Principle of Least
Privilege) для учётных записей, токенов и соединений с БД.
66. Проверяй отсутствие жёстко закодированных тестовых учётных записей или
бэкдоров.
67. Контролируй безопасность межсервисного взаимодействия (mutual TLS,
подпись запросов, валидация JWT).
68. Требуй защиты от Timing Attacks при сравнении секретов и токенов
(использование константного времени сравнения).
69. Проверяй корректность очистки оперативной памяти при работе с
чувствительными данными (пароли, криптографические ключи).
70. Проводи регулярный аудит прав доступа к инфраструктурным компонентам.

Результат синтеза дискуссии команды из 12 экспертов (Симпозиум
Перипатетиков) о том, чего не хватает Клоду для полной автономии сверх
ТЗ, backlog, `CLAUDE.md` и `.clauderc`. Отобраны по 7 параметрам:
**сжатие контекста, детерминированность, самоисцеление, управление
состоянием, токен-эффективность, интеграция цепочек инструментов,
изоляция песочницы** — по 14 правил на параметр (98) + 1 золотое
правило автономии (99).

а не читать как манифест. Родственные артефакты, на которые эти

## Параметр 1: Сжатие контекста (Context Density) — 1–14

1. Никогда не проси переписать весь файл — требуй выводить только diff или изменённые функции.
2. Используй XML-теги (`<core\\\\\\\\\\\\\\\_logic>`, `<UI>`) для структурирования `CLAUDE.md` — Клод читает XML надёжнее, чем Markdown с неоднозначной вложенностью.
3. Разделяй ТЗ на горячий (актуальный спринт) и холодный (общая архитектура) контекст.
4. Запрети Клоду извиняться и писать введения («Конечно, вот ваш код») — только код и сухие логи.
5. Регулярно запускай промпт: «Сделай summary нашего диалога в 500 токенах, я начну новую сессию с ним».
6. Храни громоздкие данные (сложные логи, дампы БД) в сжатом виде или передавай только заголовки.
7. Используй аббревиатуры для частых команд (например, `\\\\\\\\\\\\\\\[V]` — validate, `\\\\\\\\\\\\\\\[R]` — refactor). Пропиши это в `.clauderc`.
8. Выноси историю успешных слияний веток и настройки merge-guardrails в отдельный справочник, не держи их в активном ТЗ.
9. Передавай структуру проекта через `tree -I 'node\\\\\\\\\\\\\\\_modules|.git'`, а не копированием путей вручную.
10. Если контекст переполнен, требуй ответа в формате JSON — это заставляет модель сжимать смысл.
11. Ограничь глубину анализа старого кода тремя уровнями импортов (см. `context\\\\\\\\\\\\\\\_map.json`).
12. Требуй удалять комментарии в генерируемом коде, если они дублируют название очевидной функции.
13. Настрой скрипт, который перед отправкой контекста Клоду вырезает все пустые строки и лишние табы из логов.
14. Запрети анализировать файлы, которые не менялись более месяца, если задача не касается рефакторинга ядра.

## Параметр 2: Детерминированность (Determinism) — 15–28

15. Всегда задавай роль до передачи задачи: «Ты — Senior Cloud Architect...».
16. Указывай конкретную версию языка и фреймворка (например, Python 3.11, FastAPI 0.110).
17. Требуй пошагового рассуждения (Chain of Thought) через тег `<thought\\\\\\\\\\\\\\\_process>` строго до написания кода.
18. Используй негативные промпты: чётко пиши, какие библиотеки и паттерны использовать нельзя.
19. Введи штрафные баллы в системном промпте: «Если ты используешь `any`/`Any` без обоснования — задача считается проваленной».

\## Часть 2: 99 лайфхаков по 7 параметрам



Параметры отбора (почему именно эти 7, а не 599 случайных советов):



1\. \*\*Сжатие контекста\*\* (Context Density) — контекстное окно конечно, а сессия длинная.

2\. \*\*Детерминированность\*\* (Determinism) — одна и та же задача должна давать предсказуемый результат.

3\. \*\*Самоисцеление\*\* (Error Recovery) — агент должен уметь диагностировать и чинить сам, не залипая в цикле.

4\. \*\*Управление состоянием\*\* (State Management) — без этого 10-я итерация автономной работы превращается в кашу.

5\. \*\*Токен-эффективность\*\* (Token Efficiency) — не то же самое, что сжатие контекста: это про стоимость каждого отдельного обмена.

6\. \*\*Интеграция цепочек\*\* (Tool Chaining) — автономность требует, чтобы инструменты вызывали друг друга, а не только человек — модель.

7\. \*\*Изоляция и безопасность\*\* (Sandboxing/Security) — особенно критично при работе с монорепозиториями, контейнерами и изолированными VM.

\### Параметр 1: Сжатие контекста (Context Density)



1\. Никогда не проси переписать весь файл — требуй diff или только изменённые функции.

2\. Используй структурные теги (`<core\_logic>`, `<UI>`) в служебных промптах, когда Markdown-заголовков недостаточно для однозначного разбора.

3\. Разделяй ТЗ на горячий (`TECHNICAL\_SPECIFICATION.md` активного спринта) и холодный (архитектура целиком) контекст — не тащи оба в одну задачу.

4\. Не извиняйся и не пиши вступления («Конечно, вот ваш код») — сразу код и сухие логи.

5\. Периодически делай summary диалога в сжатом виде для передачи в новую сессию (для этого и существует `state\_journal.md` — не полагайся на память чата).

6\. Храни громоздкие данные (логи, дампы БД) сжато или передавай только заголовки/первые и последние N строк.

7\. Используй короткие обозначения для частых операций в этом репо — например `\[V]` = запустить `validation\_protocol.md`, `\[R]` = рефакторинг с сохранением тестов.

8\. Историю успешных слияний и merge-guardrails держи в `CORRESPONDENCE\_LOG.md`, не в активном ТЗ.

9\. Передавай структуру проекта через `context\_map.json`, а не построчным перечислением путей.

10\. При переполнении контекста запрашивай ответ в структурированном формате (JSON/таблица) — это вынуждает сжимать смысл.

11\. Ограничивай глубину анализа импортов тремя уровнями, если задача не касается ядра архитектуры.

12\. Не добавляй комментарии, дублирующие очевидное имя функции (уже закреплено в CLAUDE.md стиле, здесь — явное правило).

13\. Периодически архивируй старые записи `state\_journal.md` в `docs/STATE\_JOURNAL\_ARCHIVE.md`, если файл разрастается.

14\. Не анализируй файлы, не менявшиеся >1 месяца, если задача не касается рефакторинга ядра — сверяйся с `context\_map.json` → `hot\_cold`.



\### Параметр 2: Детерминированность (Determinism)



15\. Явно задавай роль/контекст перед сложной задачей, если она выходит за рамки очевидного из структуры репо.

16\. Фиксируй версии зависимостей явно (`requirements.txt` — источник истины, не гадать).

17\. Для сложной логики — рассуждение по шагам ДО кода, не вперемешку.

18\. Явно указывай, каких паттернов/библиотек избегать (например: не добавлять `scikit-learn` как зависимость ради одного метода — см. `app/multipath\_detector.py`'s hand-rolled EM, `CORRESPONDENCE\_LOG.md` Entry 9).

19\. Type hints обязательны (уже в `CLAUDE.md`) — здесь усиление: PR/коммит с untyped-функцией в новом коде считается незавершённым.

20\. Псевдокод перед реализацией — только для новых алгоритмов уровня Rule 7 (12-phase HLD), не для тривиальных правок.

22\. Указывай сложность алгоритма (Big O) в комментарии, если цикл работает потенциально с большим N (например, DBSCAN в `object\_detection.py` уже документирован как O(n log n) через KD-tree).

23\. Краевые случаи описывай в стиле Given-When-Then при написании тестов — уже фактическая практика в этом репо (см. `tests/test\_\*\_full.py`).

25\. Формат вывода ошибок в API — уже задан в `app/main.py`: `{"error": {"code", "message", "details"?}}`. Не изобретай новый формат.

26\. Стоп-слова/условия, при которых нужно остановиться и спросить — см. `validation\_protocol.md` Step 0 (Golden Meta-Rule).

27\. Перед архитектурным решением — сверка с `CLAUDE.md` (Rules 1-8) и `TECHNICAL\_SPECIFICATION.md`, не изобретать параллельную архитектуру.

28\. Сигнатуры новых функций — с полными типами до реализации тела (уже требование PEP-8 + Rule 4 из `.clauderc`).



\### Параметр 3: Самоисцеление (Error Recovery / Self-healing)



29\. После написания нетривиального кода — самостоятельно перечитай и найди 2-3 потенциальные проблемы до того, как считать задачу законченной (аналог peer review, но от первого лица).

30\. Для новых функций с ясным контрактом ошибок — сначала тест на отказ (failure test), потом реализация (TDD, уже требование `.clauderc` Rule 28).

31\. При ошибке в тестах/консоли — сначала объясни причину, потом предложи ≥1 путь решения, не бросайся сразу переписывать код вслепую.

32\. Circuit breaker для самого себя: если 3 попытки подряд не решили задачу одним и тем же подходом — смени стратегию или задай вопрос (см. Golden Meta-Rule).

33\. Любой сетевой/внешний вызов (MAVLink, HTTP) должен иметь fallback — уже реализовано для MAVLink (`mavlink\_imu.py`: `start()` возвращает `False`, не бросает исключение).

34\. Никаких «тихих падений» — каждое перехваченное исключение логируется с контекстом (`logger.error(f"...: {e}")` — уже паттерн в этом репо, сохраняй его).

35\. При merge-конфликте — сначала пошаговый план разрешения, потом финальный файл (не молча резолвить в пользу одной стороны).

36\. При падении теста — анализируй traceback с конца (от самого глубокого вызова), не с верхнего уровня.

37\. Для сложной отладки — временно разворачивай одну строку в несколько с промежуточными `print`/`logger.debug`, потом убирай перед коммитом.

38\. Миграции/изменения схем данных (например, `MapMetadata` формат) — сопровождай обратной совместимостью загрузки (уже сделано: `load\_map` умеет читать записи без метаданных).

39\. Если предлагаемое решение ломает CI/сборку — сначала чини пайплайн/Dockerfile, потом продолжай (см. `BLIND\_SPOT\_AUDIT\_R2\_FINDINGS.md` 15-2: сломанный `EXPOSE` был найден только аудитом, не CI — не повторяй этот класс ошибки).

40\. Для асинхронного/многопоточного кода — явно проверяй race conditions (см. `app/lidar\_driver.py`'s `\_reconnect\_lock`, `app/map\_manager.py`'s atomic staging-dir pattern как образцы).

41\. При генерации кода, работающего с большими данными — учитывай пределы памяти (например, `Scanner3D.max\_points=500000` cap — не убирай подобные ограничители без замены).

42\. Распознавай циклические зависимости превентивно — сверяйся с `context\_map.json` перед добавлением нового импорта.



\### Параметр 4: Управление состоянием (State Management)



43\. Перед сложной задачей — проверь `git status`, чтобы видеть несохранённые изменения (см. `validation\_protocol.md` Step 1).

44\. Концепция чекпоинта: успешный `python3 -m pytest tests/ -q` с зелёным результатом + коммит — это checkpoint. Откат = `git log` + выбор последнего зелёного коммита, не `git reset --hard` без разрешения пользователя.

45\. Мелкие подзадачи внутри одной крупной фичи — отслеживай через `TaskCreate`/`TaskUpdate` (инструмент сессии), не создавай отдельный `todo\_temp.md`, если сессионный трекер уже доступен.

46\. Не меняй глобальное состояние (например, `Config.slam` — общий синглтон) без явного понимания, что оно общее — см. `context\_map.json` → `app/config.py`'s note про утечку между тестами.

47\. `state\_journal.md` обновляется после успешного прохождения `validation\_protocol.md`, не до.

48\. Изолируй побочные эффекты в отдельные, легко тестируемые функции/методы — уже паттерн в этом репо (`\_apply\_environmental\_correction`, `\_project\_beam` как чистые вычислительные хелперы, вызываемые из `\_process\_reading`).

49\. Для конечных автоматов (например, `LiDARSLAMApplication.MODE\_\*`) — явно документируй переходы, не полагайся на неявную логику (`set\_mode()` уже делает явные проверки при переходе из RECORDING/NAVIGATING/SCANNING).

50\. Идемпотентность: повторный вызов операции не должен ломать систему (например, `stop()`/`stop\_recording()` уже безопасны при повторном вызове — сохраняй это свойство в новом коде).

51\. Логируй смену состояний на уровне API-эндпоинтов, если это влияет на диагностику (уже частично сделано через `logger.info(f"Mode changed to: {mode}")`).

52\. В конце сессии — состояние фиксируется в `state\_journal.md`, а не только в памяти диалога.

53\. Явно различай Dev/Test/Prod-контекст при работе с конфигурацией (`Config.DEBUG`, `LIDAR\_API\_TOKEN` — уже разделены; не смешивай тестовые и продовые значения).



\### Параметр 5: Токен-эффективность (Token Efficiency)



54\. Используй короткие команды вместо длинных объяснений там, где смысл однозначен (см. Параметр 1 #7).

55\. Держи `.claudeignore` актуальным и агрессивным (см. созданный файл) — не читай бинарники/дампы/кэши в контекст.

56\. Передавай сигнатуры/интерфейсы вместо целых файлов, если меняется только одна функция.

57\. Не вставляй неизменившиеся блоки импортов повторно в объяснения.

58\. Служебные заметки/комментарии для внутреннего использования — на английском (токенизируется плотнее кириллицы); пользовательские ответы — на языке пользователя.

59\. Короткий, но читаемый синтаксис (тернарники, list comprehension) — там, где не вредит ясности (уже стиль проекта, см. `app/\*.py`).

60\. Не дублируй большие повторяющиеся блоки в документации — используй ссылки/паттерн «см. выше», как уже делает `TECHNICAL\_SPECIFICATION.md`.

61\. При анализе больших JSON/массивов — работай с репрезентативным сэмплом, не всем массивом, если задача не требует полного прохода.

62\. Не генерируй README/итоговые отчёты по недоделанной работе — только когда задача реально завершена (текущий `README.md` уже отражает готовый продукт, не черновик).

63\. Для промежуточных внутренних шагов — держи ответы компактными, разворачивай подробности только в финальном результате.

64\. При поиске бага в длинном логе — фильтруй регулярками (таймстемпы, `INFO`-шум) перед тем, как нести в контекст.

65\. Правило для служебных сообщений: без вежливых вступлений, сразу суть — это уже стиль этой сессии, закрепляем письменно.

66\. Многоступенчатый подход к патчам: сначала локализовать (номера строк/имя функции), потом патчить именно это место, не весь файл.

67\. Конфигурации инфраструктуры — YAML предпочтительнее JSON там, где формат не диктуется инструментом (Docker Compose уже YAML; `context\_map.json` — JSON, потому что это машиночитаемый артефакт для инструментов, не для экономии токенов).



\### Параметр 6: Интеграция цепочек (Tool Chaining)



68\. Для повторяемых операций — оформляй как bash-скрипт/тест, не как разовую ручную последовательность команд.

69\. Перед интеграцией стороннего API — сначала протестируй его напрямую (curl/минимальный скрипт), потом встраивай.

70\. Контракт до реализации: для новых REST-эндпоинтов — сигнатура/схема ответа фиксируется в коде (`error\_response()` уже задаёт стандартную форму) до того, как обрастает деталями.

71\. CI-конфигурация (`.github/workflows/`) должна появляться одновременно с серверной логикой, которую она проверяет — сейчас CI отсутствует, это зафиксировано как приоритет №1 в `DEVELOPMENT\_BACKLOG.md` Section 7.

72\. Для локального запуска/отладки — предпочитай существующие `Bash`-инструменты сессии над изобретением новых промежуточных скриптов, если задача одноразовая.

73\. Связывай генерацию кода с реальной проверкой: код → тест → (если нужно) профилирование, а не «код → считаем готовым».

74\. Multi-stage Docker-сборки — уже паттерн в `Dockerfile`/`Dockerfile.arm64` (последний требует ревизии, см. `BLIND\_SPOT\_AUDIT\_R2\_FINDINGS.md` 15-7); не откатывайся на single-stage без причины.

75\. Секреты — только через переменные окружения/`LIDAR\_API\_TOKEN`, никогда не хардкодить в коде или конфигах, коммитящихся в git.

76\. Для новых REST-эндпоинтов — добавляй пример вызова в `docs/API.md`, если он документирован там (проверь перед добавлением).

77\. Цепочка «парсер → данные → анализ аномалий» — уже реализована как `data\_quality.py` → `slam\_engine.py`/`localization.py`; новые сенсорные пайплайны следуй тому же паттерну (валидация перед потреблением).

78\. Для новых сервисов/модулей с чётким контрактом — описывай интерфейс (function signatures/dataclass) до реализации внутренней логики.

79\. Healthcheck-паттерн уже есть (`/api/health`, `Dockerfile`'s `HEALTHCHECK`) — любой новый изолированный процесс (например, будущий MAVLink-мост) должен получить аналог.

80\. Линтер/тест-цикл — уже частично автоматизирован через `validation\_protocol.md` Step 3; не пропускай шаги вручную «на глаз».

81\. Для конфигураций многих однотипных узлов (например, будущая multi-ROV поддержка, `BLIND\_SPOT\_AUDIT\_R2\_FINDINGS.md` 21-1) — генерируй списком/шаблоном, не копипастой.



\### Параметр 7: Изоляция и безопасность (Security/Sandboxing)



82\. Zero Trust по умолчанию — валидируй все входящие данные на границе (уже паттерн: `validate\_path\_component`, `safe\_join`, JSON schema-подобные проверки в `app/main.py` роутах).

83\. Никакого `eval()`/динамического исполнения строк — ни при каких обстоятельствах.

84\. CORS и rate limiting — обязательны для новых публичных API (уже реализовано через `ALLOWED\_ORIGINS`, `@require\_rate\_limit`; не добавляй роут без них).

85\. Параметризованные запросы/безопасные сериализаторы — этот проект не использует SQL, но JSON-сериализация (`json.dumps`/`json.load`) должна оставаться единственным способом (не строковая конкатенация).

86\. Локальные bash-скрипты — через инструмент `Bash` сессии, который уже sandboxed; не изобретай собственный `chroot`/эмулятор поверх него без необходимости.

87\. Docker-контейнеры — непривилегированный пользователь (уже `USER lidar\_app`/аналог в `Dockerfile`), не откатывайся на root.

88\. Зависимости сканируются на уязвимости вручную при добавлении (`requirements.txt`'s CVE-комментарии — продолжай эту практику для новых пакетов).

89\. Маскируй PII/чувствительные данные в логах — уже реализовано (`repr()` вокруг `client\_id`, токен логируется только фингерпринтом — см. `BLIND\_SPOT\_AUDIT\_R2\_FINDINGS.md` 18-8/18-9).

90\. Токены/ключи — только через переменные окружения, никогда в конфиг-файлах, коммитящихся в git (см. #75, дублируется намеренно — это разные секции по Критику, но одно правило).

91\. Защитные буферы/лимиты при обработке больших массивов — уже есть паттерн (`Scanner3D.max\_points`, `DataQualityValidator`'s rolling window) — сохраняй cap'ы в новом коде.

92\. Принцип наименьших привилегий — для новых интеграций (например, будущий доступ к облачному хранилищу карт) запрашивай минимально необходимые права.

93\. Не используй непроверенные/сомнительные Docker-образы — `Dockerfile.arm64` уже пинит `nvcr.io/nvidia/l4t-pytorch` официальный образ; держи эту дисциплину.

94\. CSP/security headers для фронтенда — отмечено как незакрытая находка (`BLIND\_SPOT\_AUDIT\_R2\_FINDINGS.md` 18-12), не забывай при следующей итерации фронтенда.

95\. При написании скриптов, обращающихся к внешним сервисам (сканирование сети, скрапинг) — уважай rate limits, обрабатывай HTTP 429, не создавай нагрузку, похожую на атаку (согласуется с общим запретом на DoS-подобное поведение в системных инструкциях сессии).
