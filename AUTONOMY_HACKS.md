# 99 Идеальных Лайфхаков для Автономного Кодирования

**Источник**: Симпозиум Перипатетиков — обсуждение 12 экспертов (креативный
дизайнер, скептичный критик, дотошный аналитик) о том, чего не хватает
Клоду для полной автономии в этом проекте. Синтезированный результат:
машинная логика вместо антропоморфных метафор, 7 параметров отбора вместо
произвольного списка, явный механизм забывания (garbage collection) для
контекстного окна.

**Статус**: живой документ. Следуй этим правилам по умолчанию в этом
репозитории; они дополняют, а не заменяют `.clauderc` (99 правил
инженерной дисциплины) и `CLAUDE.md` Rules 1-8. Где есть конфликт — `.clauderc`
Rule 99 (главный закон: 95%+ покрытие, ноль слепых зон, соответствие ТЗ)
имеет приоритет.

**Связанные артефакты**: `state_journal.md`, `validation_protocol.md`,
`.claudeignore`, `context_map.json` — эти четыре файла реализуют
инфраструктуру, которую данный документ описывает как правила. См.
`CLAUDE.md` Rule 8 для точки входа.

## Часть 2: 99 лайфхаков по 7 параметрам

Параметры отбора (почему именно эти 7, а не 599 случайных советов):

1. **Сжатие контекста** (Context Density) — контекстное окно конечно, а сессия длинная.
2. **Детерминированность** (Determinism) — одна и та же задача должна давать предсказуемый результат.
3. **Самоисцеление** (Error Recovery) — агент должен уметь диагностировать и чинить сам, не залипая в цикле.
4. **Управление состоянием** (State Management) — без этого 10-я итерация автономной работы превращается в кашу.
5. **Токен-эффективность** (Token Efficiency) — не то же самое, что сжатие контекста: это про стоимость каждого отдельного обмена.
6. **Интеграция цепочек** (Tool Chaining) — автономность требует, чтобы инструменты вызывали друг друга, а не только человек — модель.
7. **Изоляция и безопасность** (Sandboxing/Security) — особенно критично при работе с монорепозиториями, контейнерами и изолированными VM.

### Параметр 1: Сжатие контекста (Context Density)

1. Никогда не проси переписать весь файл — требуй diff или только изменённые функции.
2. Используй структурные теги (`<core_logic>`, `<UI>`) в служебных промптах, когда Markdown-заголовков недостаточно для однозначного разбора.
3. Разделяй ТЗ на горячий (`TECHNICAL_SPECIFICATION.md` активного спринта) и холодный (архитектура целиком) контекст — не тащи оба в одну задачу.
4. Не извиняйся и не пиши вступления («Конечно, вот ваш код») — сразу код и сухие логи.
5. Периодически делай summary диалога в сжатом виде для передачи в новую сессию (для этого и существует `state_journal.md` — не полагайся на память чата).
6. Храни громоздкие данные (логи, дампы БД) сжато или передавай только заголовки/первые и последние N строк.
7. Используй короткие обозначения для частых операций в этом репо — например `[V]` = запустить `validation_protocol.md`, `[R]` = рефакторинг с сохранением тестов.
8. Историю успешных слияний и merge-guardrails держи в `CORRESPONDENCE_LOG.md`, не в активном ТЗ.
9. Передавай структуру проекта через `context_map.json`, а не построчным перечислением путей.
10. При переполнении контекста запрашивай ответ в структурированном формате (JSON/таблица) — это вынуждает сжимать смысл.
11. Ограничивай глубину анализа импортов тремя уровнями, если задача не касается ядра архитектуры.
12. Не добавляй комментарии, дублирующие очевидное имя функции (уже закреплено в CLAUDE.md стиле, здесь — явное правило).
13. Периодически архивируй старые записи `state_journal.md` в `docs/STATE_JOURNAL_ARCHIVE.md`, если файл разрастается.
14. Не анализируй файлы, не менявшиеся >1 месяца, если задача не касается рефакторинга ядра — сверяйся с `context_map.json` → `hot_cold`.

### Параметр 2: Детерминированность (Determinism)

15. Явно задавай роль/контекст перед сложной задачей, если она выходит за рамки очевидного из структуры репо.
16. Фиксируй версии зависимостей явно (`requirements.txt` — источник истины, не гадать).
17. Для сложной логики — рассуждение по шагам ДО кода, не вперемешку.
18. Явно указывай, каких паттернов/библиотек избегать (например: не добавлять `scikit-learn` как зависимость ради одного метода — см. `app/multipath_detector.py`'s hand-rolled EM, `CORRESPONDENCE_LOG.md` Entry 9).
19. Type hints обязательны (уже в `CLAUDE.md`) — здесь усиление: PR/коммит с untyped-функцией в новом коде считается незавершённым.
20. Псевдокод перед реализацией — только для новых алгоритмов уровня Rule 7 (12-phase HLD), не для тривиальных правок.
21. Стиль именования — `snake_case` для Python (PEP-8, уже задан), без исключений.
22. Указывай сложность алгоритма (Big O) в комментарии, если цикл работает потенциально с большим N (например, DBSCAN в `object_detection.py` уже документирован как O(n log n) через KD-tree).
23. Краевые случаи описывай в стиле Given-When-Then при написании тестов — уже фактическая практика в этом репо (см. `tests/test_*_full.py`).
24. Не используй устаревшие/deprecated API — сверяйся с `requirements.txt`'s CVE-комментариями перед добавлением зависимости.
25. Формат вывода ошибок в API — уже задан в `app/main.py`: `{"error": {"code", "message", "details"?}}`. Не изобретай новый формат.
26. Стоп-слова/условия, при которых нужно остановиться и спросить — см. `validation_protocol.md` Step 0 (Golden Meta-Rule).
27. Перед архитектурным решением — сверка с `CLAUDE.md` (Rules 1-8) и `TECHNICAL_SPECIFICATION.md`, не изобретать параллельную архитектуру.
28. Сигнатуры новых функций — с полными типами до реализации тела (уже требование PEP-8 + Rule 4 из `.clauderc`).

### Параметр 3: Самоисцеление (Error Recovery / Self-healing)

29. После написания нетривиального кода — самостоятельно перечитай и найди 2-3 потенциальные проблемы до того, как считать задачу законченной (аналог peer review, но от первого лица).
30. Для новых функций с ясным контрактом ошибок — сначала тест на отказ (failure test), потом реализация (TDD, уже требование `.clauderc` Rule 28).
31. При ошибке в тестах/консоли — сначала объясни причину, потом предложи ≥1 путь решения, не бросайся сразу переписывать код вслепую.
32. Circuit breaker для самого себя: если 3 попытки подряд не решили задачу одним и тем же подходом — смени стратегию или задай вопрос (см. Golden Meta-Rule).
33. Любой сетевой/внешний вызов (MAVLink, HTTP) должен иметь fallback — уже реализовано для MAVLink (`mavlink_imu.py`: `start()` возвращает `False`, не бросает исключение).
34. Никаких «тихих падений» — каждое перехваченное исключение логируется с контекстом (`logger.error(f"...: {e}")` — уже паттерн в этом репо, сохраняй его).
35. При merge-конфликте — сначала пошаговый план разрешения, потом финальный файл (не молча резолвить в пользу одной стороны).
36. При падении теста — анализируй traceback с конца (от самого глубокого вызова), не с верхнего уровня.
37. Для сложной отладки — временно разворачивай одну строку в несколько с промежуточными `print`/`logger.debug`, потом убирай перед коммитом.
38. Миграции/изменения схем данных (например, `MapMetadata` формат) — сопровождай обратной совместимостью загрузки (уже сделано: `load_map` умеет читать записи без метаданных).
39. Если предлагаемое решение ломает CI/сборку — сначала чини пайплайн/Dockerfile, потом продолжай (см. `BLIND_SPOT_AUDIT_R2_FINDINGS.md` 15-2: сломанный `EXPOSE` был найден только аудитом, не CI — не повторяй этот класс ошибки).
40. Для асинхронного/многопоточного кода — явно проверяй race conditions (см. `app/lidar_driver.py`'s `_reconnect_lock`, `app/map_manager.py`'s atomic staging-dir pattern как образцы).
41. При генерации кода, работающего с большими данными — учитывай пределы памяти (например, `Scanner3D.max_points=500000` cap — не убирай подобные ограничители без замены).
42. Распознавай циклические зависимости превентивно — сверяйся с `context_map.json` перед добавлением нового импорта.

### Параметр 4: Управление состоянием (State Management)

43. Перед сложной задачей — проверь `git status`, чтобы видеть несохранённые изменения (см. `validation_protocol.md` Step 1).
44. Концепция чекпоинта: успешный `python3 -m pytest tests/ -q` с зелёным результатом + коммит — это checkpoint. Откат = `git log` + выбор последнего зелёного коммита, не `git reset --hard` без разрешения пользователя.
45. Мелкие подзадачи внутри одной крупной фичи — отслеживай через `TaskCreate`/`TaskUpdate` (инструмент сессии), не создавай отдельный `todo_temp.md`, если сессионный трекер уже доступен.
46. Не меняй глобальное состояние (например, `Config.slam` — общий синглтон) без явного понимания, что оно общее — см. `context_map.json` → `app/config.py`'s note про утечку между тестами.
47. `state_journal.md` обновляется после успешного прохождения `validation_protocol.md`, не до.
48. Изолируй побочные эффекты в отдельные, легко тестируемые функции/методы — уже паттерн в этом репо (`_apply_environmental_correction`, `_project_beam` как чистые вычислительные хелперы, вызываемые из `_process_reading`).
49. Для конечных автоматов (например, `LiDARSLAMApplication.MODE_*`) — явно документируй переходы, не полагайся на неявную логику (`set_mode()` уже делает явные проверки при переходе из RECORDING/NAVIGATING/SCANNING).
50. Идемпотентность: повторный вызов операции не должен ломать систему (например, `stop()`/`stop_recording()` уже безопасны при повторном вызове — сохраняй это свойство в новом коде).
51. Логируй смену состояний на уровне API-эндпоинтов, если это влияет на диагностику (уже частично сделано через `logger.info(f"Mode changed to: {mode}")`).
52. В конце сессии — состояние фиксируется в `state_journal.md`, а не только в памяти диалога.
53. Явно различай Dev/Test/Prod-контекст при работе с конфигурацией (`Config.DEBUG`, `LIDAR_API_TOKEN` — уже разделены; не смешивай тестовые и продовые значения).

### Параметр 5: Токен-эффективность (Token Efficiency)

54. Используй короткие команды вместо длинных объяснений там, где смысл однозначен (см. Параметр 1 #7).
55. Держи `.claudeignore` актуальным и агрессивным (см. созданный файл) — не читай бинарники/дампы/кэши в контекст.
56. Передавай сигнатуры/интерфейсы вместо целых файлов, если меняется только одна функция.
57. Не вставляй неизменившиеся блоки импортов повторно в объяснения.
58. Служебные заметки/комментарии для внутреннего использования — на английском (токенизируется плотнее кириллицы); пользовательские ответы — на языке пользователя.
59. Короткий, но читаемый синтаксис (тернарники, list comprehension) — там, где не вредит ясности (уже стиль проекта, см. `app/*.py`).
60. Не дублируй большие повторяющиеся блоки в документации — используй ссылки/паттерн «см. выше», как уже делает `TECHNICAL_SPECIFICATION.md`.
61. При анализе больших JSON/массивов — работай с репрезентативным сэмплом, не всем массивом, если задача не требует полного прохода.
62. Не генерируй README/итоговые отчёты по недоделанной работе — только когда задача реально завершена (текущий `README.md` уже отражает готовый продукт, не черновик).
63. Для промежуточных внутренних шагов — держи ответы компактными, разворачивай подробности только в финальном результате.
64. При поиске бага в длинном логе — фильтруй регулярками (таймстемпы, `INFO`-шум) перед тем, как нести в контекст.
65. Правило для служебных сообщений: без вежливых вступлений, сразу суть — это уже стиль этой сессии, закрепляем письменно.
66. Многоступенчатый подход к патчам: сначала локализовать (номера строк/имя функции), потом патчить именно это место, не весь файл.
67. Конфигурации инфраструктуры — YAML предпочтительнее JSON там, где формат не диктуется инструментом (Docker Compose уже YAML; `context_map.json` — JSON, потому что это машиночитаемый артефакт для инструментов, не для экономии токенов).

### Параметр 6: Интеграция цепочек (Tool Chaining)

68. Для повторяемых операций — оформляй как bash-скрипт/тест, не как разовую ручную последовательность команд.
69. Перед интеграцией стороннего API — сначала протестируй его напрямую (curl/минимальный скрипт), потом встраивай.
70. Контракт до реализации: для новых REST-эндпоинтов — сигнатура/схема ответа фиксируется в коде (`error_response()` уже задаёт стандартную форму) до того, как обрастает деталями.
71. CI-конфигурация (`.github/workflows/`) должна появляться одновременно с серверной логикой, которую она проверяет — сейчас CI отсутствует, это зафиксировано как приоритет №1 в `DEVELOPMENT_BACKLOG.md` Section 7.
72. Для локального запуска/отладки — предпочитай существующие `Bash`-инструменты сессии над изобретением новых промежуточных скриптов, если задача одноразовая.
73. Связывай генерацию кода с реальной проверкой: код → тест → (если нужно) профилирование, а не «код → считаем готовым».
74. Multi-stage Docker-сборки — уже паттерн в `Dockerfile`/`Dockerfile.arm64` (последний требует ревизии, см. `BLIND_SPOT_AUDIT_R2_FINDINGS.md` 15-7); не откатывайся на single-stage без причины.
75. Секреты — только через переменные окружения/`LIDAR_API_TOKEN`, никогда не хардкодить в коде или конфигах, коммитящихся в git.
76. Для новых REST-эндпоинтов — добавляй пример вызова в `docs/API.md`, если он документирован там (проверь перед добавлением).
77. Цепочка «парсер → данные → анализ аномалий» — уже реализована как `data_quality.py` → `slam_engine.py`/`localization.py`; новые сенсорные пайплайны следуй тому же паттерну (валидация перед потреблением).
78. Для новых сервисов/модулей с чётким контрактом — описывай интерфейс (function signatures/dataclass) до реализации внутренней логики.
79. Healthcheck-паттерн уже есть (`/api/health`, `Dockerfile`'s `HEALTHCHECK`) — любой новый изолированный процесс (например, будущий MAVLink-мост) должен получить аналог.
80. Линтер/тест-цикл — уже частично автоматизирован через `validation_protocol.md` Step 3; не пропускай шаги вручную «на глаз».
81. Для конфигураций многих однотипных узлов (например, будущая multi-ROV поддержка, `BLIND_SPOT_AUDIT_R2_FINDINGS.md` 21-1) — генерируй списком/шаблоном, не копипастой.

### Параметр 7: Изоляция и безопасность (Security/Sandboxing)

82. Zero Trust по умолчанию — валидируй все входящие данные на границе (уже паттерн: `validate_path_component`, `safe_join`, JSON schema-подобные проверки в `app/main.py` роутах).
83. Никакого `eval()`/динамического исполнения строк — ни при каких обстоятельствах.
84. CORS и rate limiting — обязательны для новых публичных API (уже реализовано через `ALLOWED_ORIGINS`, `@require_rate_limit`; не добавляй роут без них).
85. Параметризованные запросы/безопасные сериализаторы — этот проект не использует SQL, но JSON-сериализация (`json.dumps`/`json.load`) должна оставаться единственным способом (не строковая конкатенация).
86. Локальные bash-скрипты — через инструмент `Bash` сессии, который уже sandboxed; не изобретай собственный `chroot`/эмулятор поверх него без необходимости.
87. Docker-контейнеры — непривилегированный пользователь (уже `USER lidar_app`/аналог в `Dockerfile`), не откатывайся на root.
88. Зависимости сканируются на уязвимости вручную при добавлении (`requirements.txt`'s CVE-комментарии — продолжай эту практику для новых пакетов).
89. Маскируй PII/чувствительные данные в логах — уже реализовано (`repr()` вокруг `client_id`, токен логируется только фингерпринтом — см. `BLIND_SPOT_AUDIT_R2_FINDINGS.md` 18-8/18-9).
90. Токены/ключи — только через переменные окружения, никогда в конфиг-файлах, коммитящихся в git (см. #75, дублируется намеренно — это разные секции по Критику, но одно правило).
91. Защитные буферы/лимиты при обработке больших массивов — уже есть паттерн (`Scanner3D.max_points`, `DataQualityValidator`'s rolling window) — сохраняй cap'ы в новом коде.
92. Принцип наименьших привилегий — для новых интеграций (например, будущий доступ к облачному хранилищу карт) запрашивай минимально необходимые права.
93. Не используй непроверенные/сомнительные Docker-образы — `Dockerfile.arm64` уже пинит `nvcr.io/nvidia/l4t-pytorch` официальный образ; держи эту дисциплину.
94. CSP/security headers для фронтенда — отмечено как незакрытая находка (`BLIND_SPOT_AUDIT_R2_FINDINGS.md` 18-12), не забывай при следующей итерации фронтенда.
95. При написании скриптов, обращающихся к внешним сервисам (сканирование сети, скрапинг) — уважай rate limits, обрабатывай HTTP 429, не создавай нагрузку, похожую на атаку (согласуется с общим запретом на DoS-подобное поведение в системных инструкциях сессии).

## 🌟 Параметр 0: Золотой Мета-Хак (Правило 99 этого документа)

**Правило делегирования сомнений**: если внутренняя оценка вероятности
успешного решения задачи с первой попытки ниже ~90% — ОСТАНОВИСЬ. Не пиши
код. Задай ровно один точный, изолированный вопрос, который снимает
конкретную слепую зону. Автономия без этого тормоза — самоуничтожение.

Формализовано как Step 0 в `validation_protocol.md` — это не декларация, а
исполняемая (в смысле процесса) проверка перед началом работы.

## Рефлексия (по мотивам вопроса симпозиума)

> «В какой степени истинная автономия ИИ сегодня упирается в ограничения
> самой модели, а в какой — в несовершенство промпт-каркасов и протоколов
> изоляции?»

Применительно к этому репозиторию: большинство реальных сбоев в этой сессии
(потеря незакоммиченных файлов при сбросе контейнера, флаки-тест из-за
расшаренного singleton-конфига, скрытый баг с алиасингом Open3D-объектов,
сломанный `EXPOSE` в Dockerfile, не пойманный ничем кроме ручного аудита)
были ошибками **протокола и дисциплины**, а не ограничениями модели —
каждая была найдена и исправлена в рамках одной сессии, без внешней помощи,
как только был применён достаточно строгий процесс проверки. Это и есть
практический аргумент в пользу `state_journal.md` +
`validation_protocol.md`: не полагаться на то, что модель «не ошибётся», а
структурировать процесс так, чтобы ошибка была дешёво обнаружима.
